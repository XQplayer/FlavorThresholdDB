# FlavorThresholdDB 岛津气质分析工作台设计

## 目标

在现有本地 FlavorThresholdDB 中增加独立的岛津 GC-MS 分析入口和页面，使用户能够上传岛津原始工作簿与样品/内标信息工作簿，选择运行方式，执行已验证的步骤0至步骤6，实时查看每一步状态、计数、日志与异常，并下载完整结果。当前范围不计算 OAV。

## 方案比较与选择

### 方案A：复用8787端口，新增独立分析模块（采用）

现有 `fema_proxy_server.py` 继续负责HTTP入口，但将岛津文件、任务、流程调用和下载逻辑委托给新的 `shimadzu_analysis_service.py`。前端新增独立页面组件，`App.jsx` 只负责路由和顶部导航。

优点是本地启动仍只有5174和8787两个端口，用户无需管理第三个进程；任务模块、阈值代理和页面模块仍保持独立。缺点是本地代理承担了更多路由，但通过委托类可以避免继续膨胀。

### 方案B：新增独立分析服务端口

岛津任务服务使用第三个端口独立运行。隔离最好，但会增加启动、健康检查、端口冲突和用户排障成本。本地单机第一版不采用。

### 方案C：全部在浏览器执行

浏览器解析并处理Excel，无需后端任务。该方案无法直接复用已经过251项测试的Node/Artifact Tool流程，也无法可靠生成当前审计工作簿、manifest和渲染验证结果，因此不采用。

## 页面与路由

- 路由：`/FlavorThresholdDB/shimadzu-analysis/`。
- 首页和阈值检索页顶部导航均增加“岛津气质分析 / Shimadzu GC-MS”。
- 新页面位于 `frontend/src/features/shimadzu/`，不得继续把工作台实现堆入大型 `App.jsx`。
- 构建时为 `shimadzu-analysis` 生成静态入口，刷新该路径仍可载入应用。

## 页面结构

1. 顶部区域显示服务可用性、分析范围“步骤0—6”、OAV关闭状态和返回阈值库入口。
2. 上传区包含两个必填文件：岛津原始 `.xlsx`、样品与内标信息 `.xlsx`。上传前显示文件名、大小和格式检查。
3. 运行参数区包含：
   - 连续模式：自动依次运行步骤0—6；
   - 逐步模式：每一步成功后停在“等待确认”，用户点击继续；
   - 任务名称：用于页面显示和下载包名称；
   - 固定规则展示：CV=30%、RRF=1、样品级内标参数来自上传模板、默认纳入内标体积、OAV关闭。
4. 步骤监控区按正式顺序显示七张状态卡：步骤0输入配置、步骤1 Hit #1、步骤2化合物筛查、步骤3平行峰面积、步骤4跨样品半定量、步骤5统计/CV/CAS/QC、步骤6矩阵拆分。
5. 每一步显示 `pending/running/PASS/WARN/REVIEW/FAIL/waiting_review`、起止时间、manifest严重度、`canAdvance`、核心计数和日志尾部。
6. 完成区显示完整性验证状态、源文件SHA-256、正式结果文件数量、旁支文件提示以及ZIP下载按钮。

## 后端任务模型

- 根目录：`_local/shimadzu/`，由现有 `.gitignore` 排除。
- 每个任务目录：`jobs/<uuid>/`，包含 `input/`、`output/`、`logs/`、`job.json` 和最终ZIP。
- 上传文件以固定服务端名称保存，原始客户端文件名只作为元数据；禁止用户输入影响路径。
- 每个任务只允许一个后台工作线程。任务状态使用锁保护并通过原子JSON替换写入。
- Node流程使用已部署的 `shimadzu-flavor-data-processing` skill。运行时在 `_local/shimadzu/runtime/skill` 建立干净副本，并把 `node_modules` Junction指向Codex捆绑依赖；不得修改部署skill或上传源文件。
- 连续模式依次调用 `v2-cli.mjs stage0` 至 `stage6`，每步完成后读取manifest和验证记录更新状态；最后调用 `verify`。
- 逐步模式每步完成后进入 `waiting_review`，继续请求只启动下一个未完成步骤。
- 任一子进程非零退出、manifest哈希错误或 `canAdvance=false` 时停止任务并标记FAIL。

## HTTP接口

- `GET /shimadzu/capabilities`：服务健康、步骤定义、固定参数、文件限制、skill状态。
- `POST /shimadzu/jobs`：multipart上传两个工作簿和JSON参数，创建任务但不自动运行。
- `POST /shimadzu/jobs/<id>/run`：启动连续模式或逐步模式的当前阶段。
- `POST /shimadzu/jobs/<id>/continue`：逐步模式继续下一阶段。
- `GET /shimadzu/jobs/<id>`：返回任务、阶段、计数、日志、输出与下载状态。
- `GET /shimadzu/jobs/<id>/download`：仅在完整性验证PASS后下载ZIP。

## 输入、安全与错误处理

- 仅接受两个 `.xlsx` 文件；单文件上限100 MB，请求总上限210 MB。
- 使用UUID任务ID、固定子目录和固定文件名；拒绝路径穿越、重复启动和非法状态转换。
- HTTP响应使用稳定错误代码，如 `INVALID_UPLOAD`、`SKILL_UNAVAILABLE`、`JOB_NOT_FOUND`、`JOB_ALREADY_RUNNING`、`STAGE_FAILED`。
- 页面断开不会取消后台任务；重新打开页面可凭任务ID恢复轮询。
- 本地分析功能只在本地服务可用时启用；GitHub Pages静态部署显示“需要本地分析服务”，不尝试浏览器内运行。

## 测试与验收

- Python单元测试覆盖任务创建、文件限制、状态转换、逐步/连续调度、失败停止、结果打包和路径安全。
- Node测试覆盖新静态路由、前端API状态规范和页面关键合同。
- 前端执行lint与build，Python执行现有测试和新增测试。
- 使用合成岛津工作簿完成一次步骤0—6本地任务，确认页面逐步更新、最终完整性PASS、ZIP可下载且OAV未生成。
- 使用浏览器检查桌面和窄屏布局、导航、上传、失败提示、刷新恢复和下载。

## 明确不做

- 本版本不计算OAV，不自动匹配阈值，不作图，不修改上传工作簿。
- 不将任务上传到Supabase或任何远程服务。
- 不在当前工作中重构整个 `App.jsx`，只增加最小路由集成。

## 工作台信息架构修订

页面采用“流程在上、操作在中、监控常驻”的科研仪器工作台结构：

1. 七节点流程图同时承担方法说明和运行状态轨道。每个节点显示该步骤的科学目的；任务开始后直接映射 `pending/running/PASS/WARN/REVIEW/FAIL`。
2. 两个上传位置分别提供配套下载。原始工作簿示例采用去标识的虚构峰记录；样品与内标模板提供三个匹配平行及当前V2字段合同，二者可以作为一对输入完成测试运行。
3. 实时监控窗口在运行前显示待机条件，运行后显示当前步骤、该步骤工作范围、manifest门禁、1.5秒轮询心跳和子进程实时日志。
4. 页面阅读顺序固定为分析思路、输入与设置、实时监控、步骤计数。保留HXQLab深绿识别色，监控区采用深色仪器控制台表面，使可编辑输入与机器状态明确分离。
5. 模板下载由后端白名单ID解析，不能使用URL读取任意任务文件或本地路径。

此次修订不改变科学规则、输出合同、步骤0至步骤6边界，也不启用OAV。
